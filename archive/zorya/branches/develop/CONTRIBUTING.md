# Робочий процес ZORYA

## Гілки
- `main` — стабільна версія, яку можна відкрити та перевірити.
- `develop` — інтеграційна гілка для поточної розробки.
- `feature/<коротка-назва>` — окрема задача або функція, створена від `develop`.
- `fix/<коротка-назва>` — виправлення помилки.

## Цикл роботи
1. Перед змінами перевірити актуальний стан `develop` і пов'язані файли.
2. Для окремої функції створити feature-гілку від `develop`.
3. Змінювати мінімально необхідну кількість файлів; не перезаписувати робочу версію цілком без потреби.
4. Перевірити синтаксис JavaScript, консоль браузера, мобільну ширину та ключові сценарії.
5. Відкрити Pull Request у `develop`, описати зміни, ризики й результати тестів.
6. Після перевірки об'єднати PR у `develop`.
7. Перевірену збірку переносити з `develop` у `main` окремим PR.

## Обов'язкові правила
- Не комітити API-ключі, паролі, токени або персональні дані.
- Не підключати реальне виконання ордерів без окремого погодження та тестового контуру.
- Реальні ринкові дані й синтетичні дані мають бути чітко розділені в коді та інтерфейсі.
- Для біржових API використовувати офіційну документацію, перевіряти ліміти запитів, тайм-аути, повторні підключення та неповні відповіді.
- Не називати симуляційний результат реальним прибутком або результатом на біржовій історії.
- Не видаляти й не перейменовувати дубльовані HTML-файли, поки не перевірено всі посилання та сценарій публікації.
- Кожна зміна має мати зрозумілий спосіб перевірки.

## Мінімальний чекліст перед PR
- [ ] JavaScript проходить перевірку синтаксису.
- [ ] Обидва HTML-файли синхронізовані.
- [ ] Основні екрани відкриваються без помилок.
- [ ] Перевірено мобільний та десктопний вигляд.
- [ ] Перевірено збереження/відновлення локальних даних, якщо вони змінювалися.
- [ ] У PR описані зміни, перевірки та відомі обмеження.
